# 解析：哪些记成交易、怎么读

## 分类：哪些会记成交易

| 类别 | 处理 |
|---|---|
| 已发生的资金变动 | 入账（`status = posted`） |
| 支付失败 | 保留记录，`status = failed`，不计入收支和余额推算 |
| 预授权、冻结 | `status = hold`，不冒充已结算消费；预授权完成、完成扣款为 `posted`；撤销/解冻为 `holdReleased`（见下「完成扣款和冻结」） |
| 验证码 | 只记日志，**不保存正文** |
| 营销、还款/账单/扣款提醒（含「将于…扣款」）、还在申请或处理中（`collect request`、`is being processed`） | 只记日志 |
| 电子账单、对账单 | 只记日志，不把历史明细再入账一遍 |
| 只有余额 | 不入账、不保存余额，**不凭余额差额编造交易**；能对上卡时记为这张卡收到过自动输入 |
| 信用额度变化，支出限额、免密上限这类设置 | 只记日志，不是资金或负债变化，写的金额是上限 |
| 钱在账户和朝朝宝之间挪动（「发起朝朝宝转入」，`Lexicon.balanceProductMove`）；用户在流水上点过「不记」的写法（见 [识别模板](templates.md) 第 7 条） | 只记日志（`skipped`），不记账、不进待处理、不发记账结果通知。朝朝宝随时能花，和账户算一个整体；别的银行的同类产品遇到了再加，没加之前由用户点「不记」 |
| 无法识别 | 通过了下面的过滤才进入待处理；可以用它做识别模板（见下） |

自动化对所有短信 / 邮件 / App 通知触发，所以先判断这条是不是用户的动账通知（`IngestEngine.run`）：

| 通知 | 处理 |
|---|---|
| 尾号或账号对得上自己的卡，或者是已添加的钱包发的（绑定了账户、用户模板认出的同样算） | 继续识别 |
| 银行或钱包发的，有金额，对不上账户 | 进待处理（可能有卡没添加） |
| 银行或钱包发的，没金额，对不上账户 | 不入账，不进待处理，只记在接收日志里（带原文，界面上不显示） |
| 有非银行的【署名】，对不上账户 | 直接丢，不保存，不写接收日志 |
| 没有署名，能完整认出交易（被截断的通知），或金额写得像银行通知（`PHP 200.00`：明确的币种加两位小数） | 进待处理 |
| 没有署名，认出了方向，但金额只是一个没写币种、没有小数的整数（聊天里的「扣除你的那份还剩50」） | 直接丢，不保存，不写接收日志（`IngestEngine.credible`） |
| 只有名称和金额（Apple 钱包的交易通知，见下） | 名称是银行或卡、提到已添加账户的银行，或币种写得明确（「JP¥」「CN¥」）时进待处理；只写「¥」「$」、名称也看不出是银行的直接丢 |
| 没有署名，正文提到已添加账户的银行或钱包，有金额（「… via Maya」） | 进待处理，这个账户列为候选 |
| 没有署名，认不出完整交易（「转我100元」） | 直接丢，不保存，不写接收日志 |

- 「银行发的」：短信号码 / 邮箱域名 / 【署名】在 `BankDirectory` 里，或【署名】里有「银行」「信用卡」「农商」「信用社」、常见银行简称等（`Lexicon.bankSignature`），
  或没有署名、正文像银行内容（`Lexicon.bankish`）。银行不全在名录里（众安、恒生、地方银行），署名不算银行就会被丢弃，所以这里宁可多算。
- 【署名】指正文开头或结尾的 `【…】`，一条短信可能有两个（「【共享流量使用提醒】…【中国移动】」）。
- **手机号形状的打码号码**（`138****0011`，共 11 位、1 开头）不是卡号，后四位不算尾号，也不用来和已添加的卡比较；打码的卡号（`6222****1234`）照常是尾号。
- 已知限制：带「尾号」字样的短信碰巧等于自己的卡（「车牌尾号 0001」），按对得上处理，会进待处理，由用户忽略。

## 交易性质（不是用户分类）

消费、入账、工资、转入、转出、退款、还款、扣息、手续费、存入、取款、利息、冲正/撤销、其他（方向明确但性质不明）。
方向（流入 / 流出）相对账户本身：信用卡消费为流出、还款为流入。只写「还款」不写方向时，按账户卡类型决定。
「支付」只说明渠道：通知写明了「收入 / 存入 / 到账」时是流入（「网上支付收入」「收入(跨行支付)」），记为其他；
「入账」不算，信用卡的「消费入账」仍是支出。
「提现收入」（「支付宝提现收入」「提现，收入金额」）是钱从钱包转到这张卡，记为转入，走转账的配对和待分类，不算取现。
英文通知没写收入还是支出、但说的是用卡或账户付了钱（`Transaction for $65.00 was approved on debit card`、`Payment of Rs 100 using … successful`）时记为消费；通知里有方向词时以方向词为准。
英文的信用卡还款常把金额夹在中间（「Payment of Rs 100 has been received on your … Credit Card」「… was credited to your card」），所以把金额前后连起来看：写了付款收到、又提到卡，就是还款。借记卡收到的钱不算还款；退款、工资仍按原来的性质。
「支取」只有写明是现金（柜台、ATM）才算取款，不计入支出：「手机银行支取」记为其他，「网上支付支取」记为消费，都计入支出。
「汇款 … 已汇出」是转出，后面的「到账」说的是收款人那边。

## 解析规则要点

- **归一化**：HTML 转文本（`<blockquote>` 标为引用）、实体解码、全角转半角、去零宽字符。
- **邮件历史**：去掉 `>` 引用行和「Original Message / 原始邮件 / 写道」之后的内容；转发邮件取转发正文。
- **金额角色**：数字前最近的标签决定含义——余额、可用额度、限额/上限、手续费、累计、应还/最低还款、积分，其余为交易金额。
  标签可以紧贴在点号后面（`UPI.Avl`、`mm.AvlBal`、`Avl.Limit`）；提醒门槛（`above the $100.00 value you set`）不是交易金额。
  紧跟在金额后面的 `bal` 也算余额（「has a $500.00 bal」）；标签和金额被逗号隔开时（「Transaction cost, Ksh0.00」）往前看。
  同一句出现两个交易金额（例如「消费 100 实际扣款 95」）视为歧义，每个金额各进一条待处理；
  用户记入其中一条，同一条通知里的其他候选金额自动忽略（拆出的手续费保留）。
  「金额（另一币种金额）」（「预授权冻结JPY1000.00（人民币48.00）」）是同一笔：括号里的是实际扣款（`EventDraft.settlement`，旧的待处理草稿没有这个字段，读出来是 nil），
  账户不持有交易币种、扣的是账户的某个币种时，按它计入那个币种的余额，不按汇率估算；账户有交易币种、余额不够整笔换成主币种扣时，
  括号里的主币种金额就是扣了多少（[ADR 0018](../../decisions/0018-ios-swift-charge-currency-and-converted-cards.md)）。括号里币种相同、或者不在括号里，仍是歧义。
  「金额10.00美元，已冻结10.00美元」也是同一笔：后一个数只是说这笔钱被冻结了。其他两个相同的金额（「消费 100，退款 100」）仍是歧义。
- **方向**：优先看紧贴金额的 DR / CR 记号，其次看离金额最近的词（金额前面取最后一个，金额后面取第一个）；金额前面写明了方向时，后面的词不能把它反过来（「you've received … It was sent by X」）；金额和标题不在一句时看整条通知。常见语言的收入、支出词在 `Lexicon.inflowCue`、`outflowCue`。
- **不是交易金额**：优惠、立减这类金额不算；`Outstanding`、`total due` 按应还处理。
- **不是金额的数字**：电话号码（`+86-138******00`、`+852 3665 3665`）、打码的号码（`138******00`、`100*0001`）、9 位以上的长数字、交易参考号；
  链接里的内容；粘在字母上的数字（交易号 `DB59HV`、车牌 `3AA33`），写了币种的除外（`USD10`）；
  已经有写明币种的交易金额时，没写币种、没有小数、后面紧跟着一个词的整数（商户「54321 testcity CN」里的 54321）；
  一段范围的开头（「1-9月补缴」「3至5天」的 1 和 3：后面那个数带着月、天、次这样的单位，`Lexicon.rangeStart`）。
- **中英双语**：同一笔写成中文、英文两段时只记一笔；英文那段认不出交易性质（其他）时以中文那段为准。
- **手续费**：「含手续费 X」→ 本金 = 总额 − X，另记一笔手续费；「转出 1000，手续费 2」→ 两笔，均不重复计算。
- **金额格式**：`1,234.56`、`1.234,56`、`12,50`、`1'234.50`、`1,20,500.75`（印度分组）；三位一组对两位小数币种是千位分隔；
  KWD 等三位小数币种的 `1.234` 视为歧义；超出币种小数位的部分全是 0 时忽略（`JPY1000.00`），不是 0 时是歧义。全部转为最小货币单位整数。
- **币种**：以通知里写明的为准（人民币/元/¥/EUR/€/USD/HK$/Rs./Ksh/RM/R$/₱/บาท…，以及 `CurrencyCode.supported` 里的全部代码，必须大写）；
  系统按手机地区写的币种也认（Apple 钱包的通知：地区不是中国大陆时人民币是「CN¥」、日元是「JP¥」，还有 CA$、AU$、NZ$、SG$、MOP$），不会只看到后面的「¥」；`Rs` 可能是几种卢比，取账户持有的；`¥` 在中文通知里优先 CNY 但保留 JPY 候选；
  通知没写币种、或只写了「元」时使用账户主币种；写了 `¥`、`$` 等多义写法时优先取账户持有的币种（多币种账户据此区分）。
  **不根据手机地区推断**。都无法确定时进入待处理。
- **时间**：交易时间按通知原文保存为「墙上时间」（不做时区换算），只写月日时按接收时间推断年份并标记；
  `03/04` 这类无法区分日月的日期不写日期；「于0618」「于20260928」按月日、年月日读；`05-10-2026`、`06-Feb-26` 这类横线写法按日月年读。交易时间与系统接收时间、App 处理时间分开保存。
- **尾号**：尾号（可以只写后三位，邮储「尾号017」）/`*[1234]`/末四位/卡号**1234/账户1234/借记卡1234/card (1234)/card ending 1234 等写法；「向尾号 XXXX 转账」「from TEST A/c ***1234」「(Mobile ending 1234)」中的是对方账户或手机。
  兴业 App 通知的「借记卡*1234*」是卡号倒数第五到倒数第二位、最后一位不显示，记成「1234*」（见下「账户匹配」）。
- **几条连在一起**：快捷指令有时把同一条通知连着交过来几遍（中间可能没有空白），整段正好是同一段文字重复几遍时只留一遍（`TextNormalizer.singleCopy`），
  和只交一遍的是同一条输入；夹在文字中间的银行【署名】后面断句（中行短信以「【中国银行】」结尾、前面没有句号），不同的几条连在一起时各记各的，不算金额有歧义。
  在正文里找已添加的卡的尾号时，不看引号里的内容：`转出至"100*0001"` 是转账对象，不是自己的卡。
- **交易对方**：商户/对方户名/在…消费/…向您转账/…向您的卡存入（含「消费退货存入」）/向…支出/转出至…/to "…"/at MERCHANT 等写法；缺失为空，不编造。摘要字段只在不是通用词（消费、转账、工资…）时作为对方。
  「在…」最长 80 个字（卡组织的商户描述带地址和邮编，地址里可以有不带空格的逗号），以「完成扣款」「预授权」「冻结」「消费」等结束，不跨过账户、卡号（「绑定在 Apple Pay 上的账户…」不是商户）。

### Apple 钱包的交易通知

「App 通知」触发把钱包的通知也交过来：只有一个名称（发卡行、卡或商户）和一个带币种符号的金额，没有「消费」「支出」这样的字
（「招商银行股份有限公司 / JP¥3,000」，用户 2026-11-10 在真机上收到的）。

- 整条通知除了金额只剩一两个名称（各 2–40 个字，没有数字和断句的标点）、金额前面有币种符号时（`MessageParser.namesBesideAmount`），读成用卡付的一笔：消费、支出。
  名称里写了性质的（「退款 JP¥3,000」）照原来的读法；支付宝、微信支付发的不这样读。
- 名称像银行或卡的（「…银行…」「银联储蓄卡」）是付款的卡，不当商户；其余的名称是商户。
- 通知里没有卡号：不直接入账，进待处理（`通知里没有卡号尾号`），名称提到的银行的卡列为候选，点一下记入；银行短信已经记过这一笔的，忽略。
  还没有和银行短信自动合并。

### 支持范围与样例依据

`Tests/BKBackendTests/ParserSampleTests.swift` 中的样例均为**按公开常见写法构造的脱敏文本**，覆盖：
招商、工商、中国银行等中文短信常见句式，英文银行卡短信 / 邮件，HTML 邮件、回复历史、转发、多笔交易邮件。
尚未用每家银行的真实通知逐一验证。用真实通知验证过的：恒生繁体短信、恒生转账邮件、恒生「無卡支付」邮件的 HTML 正文
（`Tests/BKBackendTests/HangSengEmailSamples.swift`，用户转发的真实邮件去掉转发人签名）。
识别不了的格式进入待处理；新增格式时在 `Lexicon.swift` 补词并补样例测试。
